The `khaos` command is a Rust terminal user interface built directly on `khaos_core`. It does not pass through Node.js or the TypeScript binding.

## Run the TUI

Pass the path of a recorded binary sample:

```bash
cargo run -p khaos_cli -- path/to/sample.bin
```

Cargo builds the binary and opens the terminal interface.

| Key   | Action                                      |
| ----- | ------------------------------------------- |
| `g`   | Mix the loaded sample and generate 32 bytes |
| `q`   | Quit                                        |
| `Esc` | Quit                                        |

The terminal is restored when the application exits normally.

## What the TUI shows

The sample panel reports:

- Original input size in bytes
- Bits retained by Von Neumann unbiasing
- The ratio of raw bits equal to one

The output panel displays generated bytes as hexadecimal after you press `g`.

`ones_ratio` and `unbiased_bits` describe the sample. They do not prove that the source is unpredictable.

## Build the binary

Build a debug binary while developing:

```bash
cargo build -p khaos_cli
```

Build an optimized binary for local distribution:

```bash
cargo build -p khaos_cli --release
```

The release binary is written to `target/release/khaos`.

## Current input model

The first version reads a recorded file into memory before opening the TUI. This keeps file I/O separate from entropy processing and provides a repeatable starting point for learning and tests.

The current command does not capture a webcam, microphone, temperature sensor, or radio source directly.

## Planned live mode

Live hardware support should use source adapters rather than adding device logic to the screen renderer.

```text
hardware adapter → sample channel → application state → khaos_core
                                      ↓
                                  TUI renderer
```

A source adapter will own capture and health checks. The application state will receive accepted byte samples, mix them into a long-lived pool, and expose measurements to the renderer. The renderer will only draw state and handle user input.

Planned TUI views include:

- Raw sample activity
- Unbiased bit flow
- Source health and capture failures
- Bit-distribution measurements
- Pool generation count
- Output requests
- Deterministic replay controls
- Statistical test progress

## Module layout

| File              | Responsibility                                        |
| ----------------- | ----------------------------------------------------- |
| `src/main.rs`     | Reads arguments and coordinates startup and shutdown  |
| `src/app.rs`      | Owns state, input handling, and calls to `khaos_core` |
| `src/terminal.rs` | Enters and restores terminal mode                     |
| `src/ui.rs`       | Renders application state with Ratatui                |

This separation keeps terminal drawing independent from entropy behavior and makes future source adapters easier to test.

## Security boundary

The TUI uses the same operating-system-seeded generation path as the Rust library. A loaded file is an additional physical contribution, not a replacement for the operating-system CSPRNG.

Do not use the displayed output as the only randomness source for production secrets. khaos remains experimental and unaudited.
